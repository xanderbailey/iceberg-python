# PyIceberg Table Encryption — Implementation Plan

Status: **proposal / design** · Target: PyIceberg (pure-Python)
References: `apache/iceberg` (Java, canonical) and `iceberg-rust` (sibling, already implemented)

This plan maps the Iceberg encryption spec — already implemented in Java and
Rust — onto PyIceberg's architecture. It is written to be built incrementally:
each phase is independently reviewable and lands as its own PR, per
`CLAUDE.md` ("one concern per PR", "keep the first version minimal").

---

## 1. Background: how Iceberg encryption works

Iceberg uses **two-tier envelope encryption**. Nothing except the master key
ever leaves the trust boundary in plaintext at rest.

```
  KMS (external)                    Table metadata (metadata.json)         Per-file
  ┌────────────┐  wraps   ┌───────────────────────────────┐  wraps  ┌──────────────┐
  │ master key │ ───────► │ KEK (Key Encryption Key)       │ ──────► │ DEK          │
  │ (key-id)   │          │ stored in `encryption-keys[]`  │         │ per data /   │
  └────────────┘          │ as wrapped bytes + timestamp   │         │ metadata file│
                          └───────────────────────────────┘         └──────────────┘
```

- **Master key** lives in a KMS (AWS KMS, Azure Key Vault, an in-memory test
  KMS, …). Referenced by the table property `encryption.key-id`. Only the KMS
  can wrap/unwrap with it.
- **KEK** (Key Encryption Key): generated by PyIceberg, wrapped by the master
  key via the KMS, and stored **in the table metadata** under the new v3
  `encryption-keys` array (as `EncryptedKey` records). Reused across files;
  rotated after a lifespan (Java/Rust default: 730 days, NIST SP 800-57).
- **DEK** (Data Encryption Key): a fresh random AES key per file. Wrapped by
  the KEK locally (AES-GCM) and stored in the file's `key_metadata` blob
  (for data files, in the manifest entry; for the manifest list, referenced
  from the snapshot's `key-id`).

### Two file-encryption schemes

| File kind | Scheme | Who decrypts |
|---|---|---|
| Manifest lists, manifest files, Puffin stats | **AGS1** stream (AES-GCM, 1 MiB blocks) | PyIceberg itself |
| Data / delete files (Parquet, ORC, Avro) | **Native modular encryption** (Parquet Modular Encryption) | the file-format reader (PyArrow) |

Both schemes derive their DEK + AAD prefix from the same **`StandardKeyMetadata`**
blob so key management is uniform.

### `StandardKeyMetadata` wire format (byte-compatible across engines)

```
[0x01 version byte] [Avro binary datum of:]
    encryption_key : binary  (the DEK, required)   field-id 0
    aad_prefix     : binary  (optional)            field-id 1
    file_length    : long    (optional)            field-id 2
```

The DEK must be 16/24/32 bytes (AES-128/192/256). This is the exact format
Java's `StandardKeyMetadata` and Rust's `encryption/key_metadata.rs` produce,
so cross-engine reads/writes interoperate.

### AGS1 stream format (for Avro manifest metadata)

```
Header (8 bytes): magic "AGS1" + plaintext block size u32-LE (default 1 MiB)
Block N: nonce (12B) + ciphertext (≤ block size) + GCM tag (16B)
Per-block AAD = aad_prefix || block_index (u32-LE)
```

### Spec fields (JSON, confirmed identical in Java & Rust)

- Table metadata: `encryption-keys` — array of `EncryptedKey`
  `{ "key-id", "encrypted-key-metadata" (base64), "encrypted-by-id", "properties" }`
- Snapshot: `key-id` — points at the `encryption-keys` entry wrapping that
  snapshot's manifest-list DEK.
- Manifest list entry & data file: `key_metadata` (binary) — **already present**
  in PyIceberg's Avro schemas (`manifest.py`, field 519 / 131).
- Table properties: `encryption.key-id`, `encryption.data-key-length`
  (default 16).

## 2. Current state of PyIceberg

What already exists:
- `key_metadata` fields are in the manifest & manifest-list Avro schemas
  (`pyiceberg/manifest.py`), currently always written as `None`.
- `TableMetadataV3` model exists (`pyiceberg/table/metadata.py`).
- Data reads go through `pyarrow.dataset` (`_task_to_record_batches` in
  `pyiceberg/io/pyarrow.py`).

What is missing (the work):
- **No `encryption-keys` field** on any `TableMetadata` model.
- **No `key-id`** on the `Snapshot` model.
- **No encryption manager, no KMS abstraction, no cipher code.**
- **`SUPPORTED_TABLE_FORMAT_VERSION = 2`** — encryption is a **v3** feature, so
  v3 read/write must be viable first. Encryption should gate on
  `format_version >= 3`.
- **No crypto dependency.** PyArrow bundles Parquet modular encryption, but the
  AGS1 stream for Avro manifests needs a general AES-GCM primitive. Add
  `cryptography` (pyca) as an **optional extra** (`pyproject.toml`), never a
  core dependency (per `CLAUDE.md` Boundaries).

### Key architectural constraint — data-file decryption via PyArrow

PyIceberg reads Parquet through the **dataset API** (`ds.Scanner.from_fragment`),
not `pyarrow.parquet.ParquetFile`. Per-file `FileDecryptionProperties` (the DEK
from Iceberg's `key_metadata`) must be threaded in via
`pyarrow.dataset.ParquetFragmentScanOptions(decryption_properties=...)` /
`ParquetFileFormat`. This must be validated early against the pinned PyArrow
(>=18) — **Phase 0 spike below**. If the dataset path cannot accept per-fragment
decryption properties on the supported PyArrow range, the fallback is to read
encrypted Parquet through `pyarrow.parquet.ParquetFile(decryption_properties=…)`
for the encrypted case. This risk drives sequencing.

## 3. Proposed module layout

New package `pyiceberg/encryption/` (mirrors Rust's `encryption/` module and
Java's `org.apache.iceberg.encryption`), keeping the spec core and catalog code
untouched per `CLAUDE.md` boundaries:

```
pyiceberg/encryption/
    __init__.py          # public re-exports
    key_metadata.py      # StandardKeyMetadata: encode/decode ([0x01]+Avro)
    ciphers.py           # AES-GCM primitives + AGS1 stream read/write
    kms.py               # KmsClient ABC + GeneratedKey; KmsClientFactory
    manager.py           # EncryptionManager (envelope: KEK/DEK, cache, rotation)
    io.py                # EncryptedInputFile / EncryptedOutputFile (AGS1 wrappers)
```

Spec-level additions (small, in existing files):
- `pyiceberg/table/metadata.py` — `EncryptedKey` model + `encryption_keys`
  field on `TableMetadataV3` (and the common fields path).
- `pyiceberg/table/snapshots.py` — `key_id` (`key-id`) on `Snapshot`.
- `pyiceberg/table/__init__.py` (TableProperties) — `encryption.key-id`,
  `encryption.data-key-length` constants.

## 4. Component design (Python)

### 4.1 `key_metadata.py` — `StandardKeyMetadata`
- Fields: `encryption_key: bytes`, `aad_prefix: bytes | None`,
  `file_length: int | None`.
- `encode() -> bytes` / `decode(bytes) -> StandardKeyMetadata` using the
  `[0x01][Avro]` format. Reuse PyIceberg's own Avro machinery (`pyiceberg/avro/`)
  with a fixed 3-field schema so the datum is byte-identical to Java/Rust.
- Validate DEK length ∈ {16,24,32} on both construct and decode (Rust rejects
  bad lengths off the wire — match that, it's a security property).
- Do **not** put key bytes in `__repr__`/`__str__` — redact, like Rust's
  `SensitiveBytes`. Consider a small `SensitiveBytes` wrapper that redacts and
  best-effort zeroizes (`bytearray` + clear); note Python cannot guarantee
  zeroization, so document the limitation.

### 4.2 `ciphers.py` — AES-GCM + AGS1 stream
- `AesGcmCipher`: `encrypt(plaintext, aad) -> nonce||ct||tag`,
  `decrypt(...)`. Backed by `cryptography`'s `AESGCM`. 12-byte random nonce,
  16-byte tag. Used for DEK-wrapping and single-shot encryption.
- `AesGcmOutputStream` / `AesGcmInputStream` (or functional equivalents):
  the AGS1 block format for manifest metadata. Random-access decrypt by
  computing which blocks cover a requested byte range (mirror Rust's
  `AesGcmFileRead::read(range)` and `calculate_plaintext_length`).
- Constants: `PLAIN_BLOCK_SIZE = 1 MiB`, `NONCE=12`, `TAG=16`, magic `b"AGS1"`,
  `stream_block_aad(prefix, index)`.

### 4.3 `kms.py` — pluggable KMS
- `KmsClient` (ABC), mirroring Java `KeyManagementClient` / Rust
  `KeyManagementClient`:
  - `wrap_key(key: bytes, wrapping_key_id: str) -> bytes`
  - `unwrap_key(wrapped: bytes, wrapping_key_id: str) -> bytes`
  - `supports_key_generation() -> bool`
  - `generate_key(wrapping_key_id) -> GeneratedKey` (plaintext + wrapped)
- `KmsClientFactory` ABC: `create_kms_client(properties) -> KmsClient`, resolved
  from catalog/table properties. Follow PyIceberg's existing dynamic-loading
  convention (e.g. `_import_kms_client` similar to how FileIO is loaded) so
  users set `encryption.kms-impl` = dotted path — matches Java's config-driven
  KMS selection.
- Ship an in-memory KMS for tests only (mirrors Rust
  `MemoryKeyManagementClient` and Java `UnitestKMS`). Real cloud KMS clients are
  follow-up optional extras — **never** pull `boto3` etc. into core.

### 4.4 `manager.py` — `EncryptionManager`
The heart, mirroring Java `StandardEncryptionManager` / Rust `manager.rs`:
- Constructed from table metadata + a `KmsClient` when
  `format_version >= 3` **and** `encryption.key-id` is set; otherwise a
  `PlaintextEncryptionManager` no-op (matches Java's two managers). Raise if
  `key-id` is set but no KMS client is available.
- Holds the `{key_id: EncryptedKey}` map from `encryption-keys`, an unwrapped-KEK
  cache (TTL ~1h), and `table_key_id` + `data_key_length`.
- `encrypt(output_file) -> EncryptedOutputFile`: fresh DEK + random 16-byte AAD
  prefix → `StandardKeyMetadata`.
- `add_manifest_list_key_metadata(km) -> key_id`: find/create active KEK,
  unwrap it, AES-GCM-wrap the DEK with KEK using the **KEK timestamp as AAD**
  (anti-tamper, matches Java/Rust), store a new `EncryptedKey`, return its id
  (to record on `snapshot.key-id`).
- `decrypt_manifest_list_key_metadata(key_id) -> StandardKeyMetadata`: reverse.
- KEK lifecycle: `create_kek` (via `generate_key` when the KMS supports it, else
  `wrap_key`), `find_active_kek`, `is_kek_expired` (730-day default), timestamp
  stored in `EncryptedKey.properties["KEY_TIMESTAMP"]`.
- Expose the current key set at commit time so newly created KEKs / wrapped
  entries get persisted into `TableMetadata.encryption-keys`.

### 4.5 `io.py` — encrypted file wrappers
- `EncryptedOutputFile(inner: OutputFile, key_metadata)` — AGS1-encrypts on
  write; `EncryptedInputFile(inner: InputFile, key_metadata)` — AGS1-decrypts on
  read, reports **plaintext** size from `metadata()`. Mirror Rust `io.rs`.

## 5. Read/write path integration

### Writing metadata (manifest list + manifests)
In `pyiceberg/table/update/snapshot.py` (`_commit`, `write_manifest_list`) and
`pyiceberg/manifest.py` writers:
1. When encryption is active, wrap the manifest-list `OutputFile` in an
   `EncryptedOutputFile`; record the returned key-metadata id on the snapshot's
   `key-id`; add the wrapped entry to `encryption-keys`.
2. Same for manifest files — set each `ManifestFile.key_metadata`.
3. Data files: encrypt on write (Phase 4) via Parquet modular encryption,
   setting `DataFile.key_metadata`.

### Reading metadata
In `pyiceberg/manifest.py` (`read_manifest_list`, `_manifests`): when a
`key_metadata` / snapshot `key-id` is present, resolve the DEK through the
`EncryptionManager` and wrap the `InputFile` in `EncryptedInputFile` before
handing it to the Avro reader.

### Reading data files (PyArrow)
In `_task_to_record_batches` (`pyiceberg/io/pyarrow.py`): when
`task.file.key_metadata` is set, decode `StandardKeyMetadata` → build
`FileDecryptionProperties(dek, aad_prefix)` → attach via
`ParquetFragmentScanOptions` on the fragment/format (mirrors Rust
`build_arrow_reader_options`). `FileScanTask` must carry `key_metadata` through
to this point.

## 6. Phased delivery (each = one PR)

- **Phase 0 — Spike (no merge, or a test-only PR).** Prove PyArrow dataset-path
  per-fragment `FileDecryptionProperties` on the supported PyArrow range, and
  round-trip a Parquet file encrypted by Java/Rust. Decides the read approach.
- **Phase 1 — Spec models.** `EncryptedKey` + `encryption-keys` on v3 metadata;
  `key-id` on `Snapshot`; property constants; JSON (de)serialization parity
  tests against Java/Rust fixtures. No behavior change.
- **Phase 2 — Crypto core.** `key_metadata.py` + `ciphers.py` +
  `cryptography` optional extra. Unit tests incl. **cross-engine vectors**
  (decode Java/Rust `StandardKeyMetadata` and AGS1 streams; encode ours and
  decrypt in Rust). This is where interop is nailed down.
- **Phase 3 — KMS + manager.** `kms.py`, in-memory KMS, `manager.py` with
  envelope wrap/unwrap, KEK cache + rotation. Unit tests mirror
  `manager.rs` tests (reuse, rotation, roundtrip).
- **Phase 4 — Metadata file encryption (AGS1).** Wire `EncryptionManager` into
  manifest-list / manifest write+read. Integration test: write an encrypted
  table, read it back; cross-read a Java/Rust-written encrypted table.
- **Phase 5 — Data file encryption (Parquet).** Encrypt on write, decrypt on
  read via the Phase-0 approach; wire `key_metadata` through `FileScanTask`.
- **Phase 6 — Cloud KMS + docs.** Real KMS clients as optional extras; user
  docs under `mkdocs/`; CLI/config plumbing (`encryption.kms-impl`).

v3 write support is a prerequisite for Phases 4–5; if v3 write is not yet
complete in PyIceberg, encryption write lands behind it (read-side interop can
still be built and tested against Java/Rust-produced tables first).

## 7. Testing strategy (per `CLAUDE.md`: integration over mocks)

- **Cross-engine golden vectors** are the acceptance bar: fixtures produced by
  Java (`TestStandardKeyMetadataParser`, `TestGcmStreams`,
  `EncryptionTestHelpers`) and by Rust (the `#[test]` roundtrips already in
  `key_metadata.rs`, `io.rs`, `stream.rs`, `manager.rs`) must decode in Python,
  and Python output must decode in both.
- In-memory KMS (not a mock) for manager tests, matching Rust/Java unit KMS.
- Add to existing test files where possible; reuse fixtures.
- End-to-end: encrypt a table in PyIceberg, read with Spark/Java in the
  integration Docker suite.

## 8. Security & boundaries checklist

- Validate incoming key metadata (version byte, DEK length) before use — reject
  malformed material off the wire.
- Redact key material in all `repr`/logs; best-effort zeroization (document
  Python's limits vs Rust's `zeroize`).
- KEK timestamp used as AAD when wrapping DEKs (anti-tamper) — must match
  Java/Rust exactly or cross-engine unwrap breaks.
- Consult `SECURITY-THREAT-MODEL.md` for the plaintext-DEK trust boundary (the
  standard scheme carries the DEK in `key_metadata`/`FileScanTask` in the clear
  within the process — same as Rust; document it, don't "fix" it differently).
- `cryptography` stays an **optional extra**; cloud SDKs only inside their KMS
  client modules; no public-API breaks without a `@deprecated` cycle.

## 9. Open questions for reviewers

1. **PyArrow dataset decryption** (Phase 0): does the supported PyArrow range
   accept per-fragment `FileDecryptionProperties`, or do we branch to
   `ParquetFile` for the encrypted path?
2. **v3 write readiness**: is v3 metadata write far enough along to host the
   encryption fields, or does this block on it?
3. **KMS selection UX**: dotted-path `encryption.kms-impl` (Java parity) vs. a
   registered-factory API (closer to Rust's `KmsClientFactory`)? Recommend the
   property-driven approach for engine parity, with a factory hook for
   programmatic use.
4. Scope of first cloud KMS (AWS KMS likely first) — defer to Phase 6.
